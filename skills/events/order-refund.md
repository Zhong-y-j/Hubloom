# order.refund — 总结型处理（示例）

## 目标

把退款事件整理成**可读结论**，供运营判断；**默认不调用退款/取消类写接口**。

## 步骤

1. 若 payload 含 `orderId` 且存在订单查询类 API：可只读查询订单状态（一次即可）。
2. 若无合适只读接口或查询失败：不要编造订单内容，直接基于事件 payload 总结。
3. 交 Respond：用短段落说明——事件含义、已知字段、风险点、建议人工确认项。
4. **停住**：不执行退款；若用户后续在对话里明确要求退款，再走对话确认流程（可叠加 select-before-act）。

## 禁止

- 禁止本轮事件自动 `call_api` 执行退款、取消、改价等写操作。
- 禁止编造订单金额、用户信息或审核结论。

## 完成标准

一份简洁总结，让人知道「发生了什么、缺什么信息、要不要人审」。
