# Hubloom 是什么？

> Hubloom 是 AI Agent 时代的**基座脚手架**——就像 Spring Boot 之于后端、Vue Admin 之于后台管理。

**快速把企业 API 编成私有化 Agent，策略约束下自动执行业务操作。**

它是让**现有业务系统**长出 AI 手脚的开发起点：接上 Swagger/OpenAPI，用自然语言在真实 API 上查询与办事。业务逻辑仍在你的系统里，Hubloom 做「翻译」和「路由」。

---

## 它解决什么问题？

把 Agent 接到现有业务系统时，常见要同时处理几件事：如何把 API 变成可调用的工具、如何在对话里真正完成操作，以及如何把整条链路收成可私有化、可二开的服务。

Hubloom 的做法是：**不重新发明业务系统**，而是把「对话 → 调 API → 出结果」这条路径标准化——业务逻辑仍在你原来的服务里，Hubloom 负责编排与调用。

---

## 定位：Agent 服务

Hubloom 是可私有化部署的 **Agent 服务**，业务系统仍由你自己维护。

推荐接入形态：

**浏览器 / App → 企业后端（BFF）→ Hubloom**

登录、鉴权、限流放在你的后端；Hubloom 专注编排与调工具。前端可以用演示对话页，也可以把能力嵌进自有门户。

对外主接口是对话（`/v1/chat`、resume、history）；事件（`/v1/events`）和企微回调按需开启。细节见 [API 参考](../reference/api-reference.md)。

## 能做什么？

### 主路径（先跑通这些）

- **契约即工具** — 配上 OpenAPI/Swagger，接口进入工具面，Agent 调真实 REST
- **对话即闭环** — 决策 → 调 API / 追问 / 确认 → 收工；结论用 Markdown，过程可复盘
- **Skill 规程** — 在 `skills/` 写领域 Know-how（先查什么、怎么确认、禁区）
- **两种交付** — 演示站开箱体验；或只把 Serve / Runtime 嵌进自有应用

### 按需打开（不挡主路径）

- **Events** — 业务系统推事件，Agent 主动跑一轮（见 [事件 Webhook](../advanced/webhook.md)）
- **企业微信** — 手机单聊走同一套 Agent（见 [企业微信入口](../advanced/wecom-integration.md)）
- **长期记忆 / RAG / A2A** — 跨会话沉淀、文档问答、跨 Agent 委托（均可选）

会话历史默认就有；长期记忆、RAG、事件、企微才是「开关类」能力。

### 几个具体画面

- 「查一下某某柜子状态」→ 调 API → Markdown / 表格核对
- 「创建小区再补钥匙柜」→ 多步工具调用 → 缺参追问或表单 → 确认后落库
- 业务系统 `POST /v1/events` → 无人先开口，Agent 按规程处理并写入历史
- 企微里发一句 → 同一套 Agent → 回复推回手机

界面长什么样，可看 [文档首页](../README.md) 的预览，或跑通后自己打开演示站。

## 设计上坚持什么？

**协议驱动，配置优先**  
换模型、换 Swagger，主要改配置；领域规程走 Skill，不必重写 Runtime 核心。

**嵌入优先，而非替代系统**  
业务逻辑留在你的服务里；Hubloom 负责意图到工具调用的翻译与路由。

**脚手架，按需扩展**  
给你可二开仓库、可私有化服务和可选开关；业务实现与流程编排仍由你自己的系统负责。

协议细节（MCP 等）需要时再看 [核心概念](../core-concepts/README.md)。

---

## 你负责什么？底座负责什么？

你主要做：

- 配置 LLM、Redis、Swagger
- 编写 Skill（领域规程）
- 按需定制前端，或经 BFF 嵌入门户
- 按需开启事件、企微、记忆、RAG 等

底座替你搞定：

- 工具调用（MCP）、编排与 SSE 流式回合
- 会话历史、鉴权透传、过程可观测
- Serve 产品 API（对话 / 事件 / 企微等挂载点）

业务 API 与数据仍在你的服务里；Skill 约束「怎么办事」，不代替后端实现。

## 接下来

主路径通常是：

1. 配好 LLM 和 Swagger → 对话能调真实 API  
2. 按需写 Skill → 按你们业务规矩办事  
3. 需要时再开事件 / 企微 / RAG → 同一 Runtime，多入口
